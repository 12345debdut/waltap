// where this story begins

Postgres doesn't write your data to disk
when you commit.

It writes a 200-byte log entry to the Write-Ahead Log first — and that's enough.
The actual data file might not be touched for minutes.

The write-ahead contract: if the WAL record is on disk, the change is durable. The data page can catch up later.
This is the foundation everything else in this deck is built on.

Getting events is easy. Delivering them reliably is the engineering.

EXPONENTIAL BACKOFF
100ms → 200ms → 400ms → 800ms — with jitter (0.5×–1.5×) so multiple instances don't thundering-herd the downstream.
AT-LEAST-ONCE
If Deliver() errors → don't ack the LSN. On restart, Postgres replays from the last ack'd position. Never lose events.
DEAD-LETTER QUEUE
All retries exhausted? Write event to a JSONL file. Return nil. Stream keeps flowing. Operator inspects + replays manually.

Chapter 6 · throughput

Two flush triggers. Whichever fires first.

One HTTP POST with 100 events is much cheaper than 100 individual POSTs. The trick is knowing when to send the batch.
Trigger 1

Size · buffer ≥ maxSize

Buffer fills up to 100 events → flush immediately, synchronously, inside Deliver(). No waiting.
Trigger 2

Time · maxWait elapsed

Buffer half-full at 500ms? Background timer fires → flush whatever's there. Low-traffic moments don't get stuck.
500ms
Concurrency gotcha: the timer goroutine and the Deliver() goroutine both touch the buffer.
A mutex protects it. The context for the timer-flush is captured on the first Deliver call — never a stale per-call ctx.

Why split reads?
Scale read throughput without buying a bigger primary. Reads are usually 10–100× writes in volume.
Safety property
Misrouting a read → primary = suboptimal. Misrouting a write → replica = clear error. Conservative defaults.
Transactions pinned
BEGIN → every query goes to primary until COMMIT/ROLLBACK. Even SELECTs.

// what this taught me
I understood WAL conceptually before this project.
But there's a difference between reading about replication slots and watching your code consume one.
Between knowing about the wire protocol and parsing 'Z' bytes off a TCP socket at 2 AM.
building waltap · 2026
The deepest lesson
WAL isn't a logging system that happens to enable recovery. It's a recovery system that happens to look like a log. Once that flips, replication, PITR, and CDC stop feeling like magic.
The honest truth
waltap isn't production-grade infrastructure. It's a learning project. But building it taught me more about Postgres internals than any book, course, or talk I'd consumed before.
